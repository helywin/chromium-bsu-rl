# 无窗口性能与 GPU 加速

[English](performance.md) | [简体中文](performance.zh-CN.md) · [首页](../README.zh-CN.md)

当前模拟器运行在 **CPU** 上。无窗口模式省去显示与绘图工作，不提供 CUDA 模拟。
GPU 模拟、原生环境池和共享内存观察接口都是待研究方向，尚未实现。

## 对齐整条执行路径的计数

排查吞吐时，请区分以下指标：

| 指标 | 计数方式 |
| --- | --- |
| 环境样本/秒 | 所有环境成功执行的 step 总数 |
| 向量调用/秒 | 一次推进一批环境的调用数，同时报告实际参与的环境数 |
| 模拟 tick/秒 | 累加 `actual_ticks`，包括提前终止的步进 |
| 学习更新/秒 | 实际完成的优化器更新次数，同时报告经验批量和更新节奏 |

一次向量调用推进 32 个环境，会产生 32 条样本。反过来，如果每新增一条经验就更新一次，
预填经验之后的样本率与更新率会非常接近。这项速度包含学习耗时，不能当作模拟器单独吞吐。

分别检查原生模拟、通信与解析、观察编码、动作推理、经验采样、学习、重置和日志的耗时。
部分阶段可能重叠，不能简单累加各工作线程的时间来解释总耗时。记录硬件、原生版本、
客户端实现、工作进程模型、每动作 tick 数、种子、回合上限，以及启动和预热是否计入。
重复测量相同工作负载；固定动作采样与策略训练属于不同负载。

## 为什么更多进程可能不再提速

每个 [GameClient](../chromium_rl/client.py) 拥有一个原生进程。一次请求推进游戏后，
[原生桥接层](../game/src/rl/SnapshotBridge.cpp) 通过 JSON 导出完整快照。
Python 客户端校验并构造[类型化状态对象](../chromium_rl/state.py)后才返回，
消费项目还要继续做观察编码与学习。

例如，消费项目同时发出 32 个环境 step，然后逐条收集结果，每条经验执行一次学习更新，
最后才发出下一轮动作。学习器每轮仍要串行执行 32 次更新，已完成的环境需要等待整轮结束。
增加游戏进程不会让学习器自动并行。经验批量为 32 的一次更新仍然只更新一次参数；
把 32 次连续更新换成一次更大批量的更新，会改变训练行为。

还要区分原生游戏进程和 Python 工作进程。一个 Python 进程通过线程池可以重叠管道等待，
但常规 CPython 中，Python 密集的解析和编码仍受 GIL 限制。独立 Python 工作进程的
成本与扩展情况不同，不能混用两种测试结果。参见
[Python 线程文档](https://docs.python.org/3/library/threading.html#gil-and-performance-considerations)。

缩小策略观察维数，不会自动减少快照序列化和解析。如果先编码完整观察再截取其中一部分，
完整编码的开销依然存在。使用自写协议客户端的消费项目，也不会自动获得本仓库
Python 客户端优化的收益。

## CPU 优化方向

先分析实际消费项目，再选择修改位置。检查动作推理是否已经批量执行、数学库线程数
是否已经限制、日志是否已经缓冲；不要把已经完成的优化当作尚未解决的瓶颈。

运行时可研究带版本的二进制数组接口与批量传输，明确对象容量、掩码和溢出处理。
保留完整诊断快照，以及终止观察、事件语义和重置边界。原生多线程环境池需要先将
[Global](../game/src/Global.h) 及相关随机数、游戏对象的进程级状态拆成独立实例。
这些改造都需要新的原生行为验证，并由消费项目接入。

## 两类不同的 GPU 改造

**GPU 学习**把策略、学习批量与更新计算放到 GPU。小网络频繁执行小批量更新时，
内核派发、数据传输和同步可能比计算本身更耗时。仅迁移模型不够，输入和经验批量
也必须使用兼容设备。每次更新的 `.item()` 和依赖 GPU 结果的 CPU 分支会引入等待。
CUDA Graph 可以减少合适的固定计算段的派发开销，但不能直接捕获同步操作和不支持的
动态控制流。调整这一边界时要保留非有限值检查与失败诊断。参见
[PyTorch 性能指南](https://docs.pytorch.org/tutorials/recipes/recipes/tuning_guide.html#avoid-unnecessary-cpu-gpu-synchronization)
与 [CUDA Graph 约束](https://docs.pytorch.org/docs/stable/notes/cuda.html#constraints)。

**GPU 模拟**需要另外实现批量移动、生成、碰撞、伤害、拾取、终止、重置和状态导出。
环境状态保存在设备数组中，观察与策略张量使用同一设备。现有链式对象、全局状态和
按顺序执行的更新，无法仅靠切换编译参数搬到 GPU。

我们的工程判断是：针对这个游戏的规则，自定义
[NVIDIA Warp](https://nvidia.github.io/warp/stable/) 或 CUDA 内核，比接入整套
[Isaac Lab / Isaac Sim](https://isaac-sim.github.io/IsaacLab/main/source/setup/ecosystem.html)
更直接。这是设计方向，不是已交付后端或实测加速结论。CPU 原版应保留为行为参考，
对照碰撞顺序、事件计数、随机数序列和回合边界。不同浮点与随机数实现需要新的证据，
不能直接继承当前的同种子重复性声明。

改变动作重复次数、经验采样、更新频率或异步策略时序，也会改变实验。
吞吐与学习质量应分别报告，运行时优化应保持 [API 语义](api.zh-CN.md)。
